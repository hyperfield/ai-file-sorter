# macOS UI and Build Compatibility

## Summary

Commits `5061ffa`, `4dc9d56`, `a16c751`, `f3f1826`, `4627027`, `308130f`, and `1da581a` form a macOS- and desktop-polish sequence around early February 2026:

- libzip/CMake flags were stabilized for macOS builds
- LLM selection controls and disclosure visuals were adjusted for macOS conventions
- benchmark wording was refined
- the app gained support for macOS display-name overrides
- a small dialog appearance condition bug in the LLM selection dialog was fixed

## Motivation

The app had accumulated several rough edges on macOS:

- build-system flags that were less robust than they should be
- UI affordances that felt more Windows/Linux-centric than macOS-native
- a display-name requirement for certain macOS packaging/branding scenarios

Individually these were small, but together they affected perceived quality and packaging reliability.

## Implementation

This sequence mixed build and UI work:

- refine build flags for libzip on macOS
- tighten the LLM selection dialog layout/control behavior on macOS
- use disclosure/icon choices that fit macOS better
- support alternate application display names
- remove an appearance-condition bug that could make the LLM dialog choose the wrong visibility state

## Validation

Validation here was mostly platform-specific smoke checking:

- macOS build and packaging confirmation
- UI inspection of the LLM selection dialog and benchmark copy
- verification that display-name override paths behaved correctly

## User-visible impact

macOS users should see a cleaner and more native-feeling interface around the selection dialog and related UI, while builders get a more stable platform-specific build path.

## Remaining caveats

These commits polish compatibility and presentation; they do not eliminate the broader difference between macOS and the other desktop targets. Some runtime and packaging quirks still depend on upstream Qt, Homebrew, and local toolchain state.
